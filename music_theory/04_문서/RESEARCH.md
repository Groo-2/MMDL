# 음악 이론 데이터셋: 프로젝트 설명과 연구 근거

**데이터 버전: v2.2**

이 프로젝트는 Qwen3-VL이 음악 이론의 개념을 설명하고, 주어진 음이름과 수치에 이론을 적용하도록 학습하기 위한 자료입니다.
음정, 음계, 화음, 리듬 등의 문제를 영어로 제시하고, 설명 뒤 마지막 줄에 최종 정답을 쓰도록 학습합니다.
v2.2에서는 기존 문항과 정답을 유지한 채 입력과 응답 형식, 학습 후 평가 경로를 팀 baseline에 맞췄습니다.

이 문서는 프로젝트의 목적과 제작 원리를 설명합니다. 실제 실행 명령은 [PIPELINE.md](PIPELINE.md)에 있습니다.

## 1. 학습 영역

음악 이론을 이해하는 데에는 두 가지 능력이 필요합니다.

| 학습 유형 | 다루는 내용 |
| --- | --- |
| 개념 이해 | 이론 용어의 정의, 개념 간 구분과 오개념 교정 |
| 규칙 적용 | 음정, 음계, 화음, 리듬과 화성 규칙에 따른 계산과 판단 |

따라서 데이터에는 개념 설명과 오개념 수정, 정답을 계산하는 문제를 함께 넣었습니다.
같은 개념을 여러 음이름, 조성, 리듬과 수치로 연습하도록 구성했습니다.

## 2. 데이터 구성

| 학습 영역 | 학습 | 개발 | 최종 평가 |
| --- | ---: | ---: | ---: |
| 음정 판별과 이조 | 720 | 72 | 72 |
| 음계, 선법과 음계도수 | 390 | 39 | 39 |
| 화음의 구성, 종류와 전위 | 480 | 48 | 48 |
| 리듬 길이, 마디 완성과 템포 계산 | 750 | 75 | 75 |
| 로마숫자 분석과 종지 | 450 | 45 | 45 |
| 개념 정의, 개념 구별과 오개념 수정 | 210 | 21 | 21 |
| 합계 | 3,000 | 300 | 300 |

- **학습셋:** 모델 가중치를 학습하는 3,000문항. 객관식과 단답형이 각각 1,500문항입니다.
- **개발셋:** 학습 설정과 체크포인트를 고르는 300문항입니다.
- **최종 평가셋:** 설정 확정 후 학습 전후를 비교하는 300문항입니다.

개발셋과 최종 평가셋은 4지선다입니다. 각 세트의 정답 위치 A/B/C/D를 75문항씩 배분했습니다.
기본 이론 기준은 서양 조성음악과 12평균율이며, 음이름의 철자와 옥타브를 구분합니다.

## 3. 데이터 제작 방식

문제 유형과 이론 규칙을 설계하고, 프로그램이 새로운 문항을 생성하도록 만들었습니다.

1. **이론 규칙 정의:** 음정의 반음 수, 음계의 음 간격, 화음의 구성음과 리듬 길이를 코드로 표현합니다.
2. **새 문제 조합 생성:** 음이름, 조성, 음역, 화음 전위와 수치를 바꿔 문제 상황을 만듭니다.
3. **정답과 설명 계산:** 생성한 문제의 구조 정보를 이용해 정답과 짧은 근거를 구합니다.
4. **객관식 보기 구성:** 비슷한 음정이나 같은 수의 구성음을 가진 다른 화음 등 혼동하기 쉬운 답을 보기로 만듭니다.
5. **문제군별 분할:** 같은 계산 사례에서 파생된 문항을 묶어 학습, 개발, 최종 평가 중 한 곳에 배치합니다.
6. **검증과 저장:** 계산 결과를 재검산하고 문장 중복과 입력 형식을 확인한 뒤 JSONL 파일로 저장합니다.

`JSONL`은 한 줄마다 학습 예제 하나를 저장하는 파일 형식입니다.
실제 학습 파일의 `messages`는 user와 assistant 두 역할로 구성합니다.
user 입력은 baseline의 `mmmu_pro_cot` 프롬프트를 재사용하고, assistant 응답은 설명 뒤 마지막 줄에 `Answer:`를 둡니다.
개발 및 최종 평가 질문에도 같은 user 입력을 사용합니다.
정답 계산에 사용한 수치와 규칙은 별도의 검수 기록에 보관합니다.

## 4. 참고 연구와 적용 근거

### ChatMusician: 지식과 추론을 함께 다루는 구성

ChatMusician은 언어모델을 음악 자료로 학습시키고 MusicTheoryBench로 음악 이해 능력을 평가한 연구입니다.
MusicTheoryBench는 음악 지식과 음악 추론을 구분합니다.
이 프로젝트에서는 그 구분을 참고해 개념 설명, 오개념 수정과 규칙 계산 문항을 함께 구성했습니다.
[ChatMusician 논문, Findings of ACL 2024](https://aclanthology.org/2024.findings-acl.373/),
[MusicTheoryBench 설명](https://huggingface.co/datasets/m-a-p/MusicTheoryBench)

### SSMR-Bench: 이론 규칙으로 문제와 정답을 생성하는 방법

SSMR-Bench 연구는 음악 이론 규칙을 프로그램 함수로 구현해 정답을 검증할 수 있는 문제를 합성합니다.
논문에서는 이 합성 데이터를 검증 가능한 보상을 사용하는 강화학습에도 활용했습니다.

이 프로젝트에서 참고한 부분은 **규칙으로 새 문제를 생성하고 정답을 자동으로 확인하는 원리**입니다.
자체 규칙과 질문 틀을 구현하고, 생성된 문제에 정답과 짧은 설명을 붙여 SFT 데이터로 구성했습니다.
[SSMR-Bench 논문, 2025, 참고 버전 v1](https://arxiv.org/html/2509.04059v1)

### LoRA: 언어모델 어댑터 학습

이 프로젝트의 학습 코드는 Qwen3-VL 언어모델의 attention 층에 LoRA를 적용하도록 설정했습니다.
팀 baseline을 기준 모델로 두고, 추가 학습한 어댑터를 적용한 모델과 성능을 비교합니다.
[LoRA 논문, Hu et al., ICLR 2022](https://arxiv.org/abs/2106.09685)

## 5. 학습 및 모델 선택 설정

| 항목 | 적용 방식 |
| --- | --- |
| 학습 방식 | 음악 이론 텍스트 데이터에 대한 SFT |
| 학습 대상 | Qwen3-VL 언어모델 attention의 q/k/v/o projection에 적용한 LoRA |
| 입력 형식 | baseline 프롬프트를 사용하는 user와 assistant의 `messages` |
| 응답 형식 | 설명 뒤 마지막 줄에 `Answer:` |
| 기본모델 | `Qwen/Qwen3-VL-4B-Instruct`의 `ebb281ec70b05090aa6165b016eac8ec08e71b17` revision |
| 손실 계산 | assistant 응답 토큰에만 적용 |
| 체크포인트 선택 | 개발셋 손실 기준 |

학습과 병합에는 Transformers 4.57.1과 PEFT 0.17.1을 사용합니다.
평가는 별도 환경의 vLLM 0.27.1에서 수행하며, 해당 버전은 Transformers 5.5.3 이상을 요구합니다.
두 환경을 분리해 학습 requirements가 baseline 평가 환경을 변경하지 않도록 합니다.
[vLLM 0.27.1 패키지 의존성](https://pypi.org/pypi/vllm/0.27.1/json),
[팀 baseline 실행 기준](../../baseline/README_mmmu_eval.md)

학습 후 어댑터를 같은 원본 revision에 병합하고 전체 모델과 멀티모달 processor를 저장합니다.
이 병합 모델을 기존 baseline 평가 경로에 연결합니다.
구체적인 학습 인자와 실행 명령은 [PIPELINE.md](PIPELINE.md)에 정리했습니다.
[Hugging Face SFT 데이터 형식](https://huggingface.co/docs/trl/sft_trainer),
[PEFT LoRA 문서](https://huggingface.co/docs/peft/developer_guides/lora)

## 6. 데이터 분리와 검증

같은 문제를 표현만 바꿔 학습과 평가에 나눠 넣으면 기억한 답을 맞히는 결과가 섞일 수 있습니다.
이를 관리하기 위해 다음 변형을 같은 문제군으로 묶었습니다.

- 같은 음이름 쌍의 역질문, 옥타브 이동, 단순음정과 복합음정 변형
- 같은 화음의 구성음, 종류, 전위와 분석 질문
- 같은 음계의 구성음과 음계도수 질문
- 순서나 전체 길이의 배율이 달라도 같은 비율 구조를 가진 리듬

계산 문항은 생성기의 산술 코드와 별도로 music21 및 분수 연산으로 재검산했습니다.
일반 개념 설명은 검수 화면과 기록 양식으로 음악 전공자가 확인하도록 구성했습니다.
[music21 음정 계산 API](https://music21.org/music21docs/moduleReference/moduleInterval.html)

공개 평가 자료는 별도 비교 목록으로 관리했습니다.
MusicTheoryBench, MMMU Music, MMMU-Pro, SSMR-Bench와 팀 pilot20의 평가 텍스트
9,151레코드를 대조해 정규화된 동일 문장과 설정 기준 이상의 유사 문장 0건을 확인했습니다.
검사 대상은 질문 텍스트이며, 결과와 기준은 `03_기타/검증기록/public_eval_screening.json`에 있습니다.

최종 평가의 목적은 **학습한 이론을 새로운 음이름과 수치 조합에 적용하는 능력**을 확인하는 것입니다.

## 7. 학습과 평가 순서

1. 음악 이론 문항을 검수하고 고정 revision 원본의 개발셋 결과를 저장합니다.
2. 학습 환경에서 학습 3,000문항으로 LoRA를 학습하고 개발 손실로 체크포인트를 선택합니다.
3. 같은 환경에서 원본과 어댑터를 병합하고 모델, tokenizer와 멀티모달 processor를 저장합니다.
4. 평가 환경에서 병합 모델을 vLLM으로 실행하고 개발 결과로 학습 설정을 선택합니다.
5. 설정 확정 후 최종 평가 300문항에 대해 원본과 병합 모델을 같은 조건으로 비교합니다.
6. 기존 MMMU 평가 스크립트에 병합 모델을 연결해 Music과 전체 900문항 점수를 확인합니다.

내부 텍스트 평가는 이론 적용 능력의 변화를, 기존 MMMU 평가는 팀의 최종 목표 성능 변화를 확인하는 역할입니다.
`02_평가용/score.py`는 정확도, 개선/악화 문항 수, 문제군 단위 bootstrap 신뢰구간과 McNemar 통계를 기록합니다.
신뢰구간은 점수의 변동 범위를 함께 보는 데 사용합니다.

텍스트 평가도 baseline의 프롬프트, 생성 설정, 규칙 파서와 judge를 재사용합니다.
생성 조건은 temperature 0.7, top_p 0.8, top_k 20, repetition_penalty 1.0,
presence_penalty 1.5, seed 42와 최대 생성 32,768토큰입니다.
평가 서버는 bfloat16과 문맥 한도 40,960토큰을 사용합니다.
학습 정답의 형식은 마지막 `Answer:`로 통일하되, 평가에서는 기존 baseline 파서의 추출 규칙을 그대로 유지합니다.
원본과 병합 모델의 경로 차이는 허용하고, 공통 원본 revision과 평가 조건이 같은지 검사합니다.

실행할 때는 `MMDL/baseline/`과 `MMDL/music_theory/`의 위치를 유지합니다.
코드는 baseline 구현, 공통 도구와 검증 기록을 함께 참조합니다.

진행 순서는 **데이터 및 baseline 정합성 검사 → 음악 전공자 검수 → GPU 학습과 병합 → 최종 평가**입니다.
코드, 데이터와 모의 HTTP 검증 결과는 검증 기록에 보관하고, 실제 GPU 학습과 성능 실험은 실행 manifest로 기록합니다.
