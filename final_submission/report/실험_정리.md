작성 2026-11-17. 표와 그림은 같은 폴더의 `tables/`, `figures/`에 있고, `scripts/make_all.py`가 원본 결과에서 다시 만든다.

## 0. 한눈에 보기

**목표**: MMMU validation 전체 정확도가 base보다 높고, Music(30문항)도 base보다 높은 모델. 모델은 Qwen3-VL-4B-Instruct(bf16, 양자화 없음)로 고정하고 평가 프롬프트, sampling, 해상도, 파서, judge는 동결.

**제출 모델**: DPO(DeepVision 쌍 + MusiXQA 쌍) = `dpo_dvmx1`.

| 모델 (cu130, 같은 환경, 2 seed) | MMMU 전체 Avg@2 | base 대비 (95% 구간) | Music Avg@2 | 잘림 |
|---|---|---|---|---|
| base | 61.56% | - | 18.3% | 105 / 104 |

> base의 cu130 값은 요청 오류 8건을 재시도한 **최종본**이다(재시도 전 61.39%에서 +3문항, Music 7 → 8). 모든 모델의 요청 오류는 0이다.
> 세 모델끼리의 전체 점수 차이(최대 1.6%p)는 통계적으로 구분되지 않는다(표 2). 제출 모델이 가장 높다고 해서 "더 낫다"고 단정할 수 없다.

**핵심 발견** (각각 아래 절에서 근거를 제시)
1. 우리가 실패한 이유와 성공한 이유가 같은 곳에 있다: **응답이 끝나지 않는 루프(32,768토큰까지 이어지는 반복)** 다. base는 900문항 중 약 100개가 끝나지 않는다.
2. 성공한 모델들의 이득은 거의 전부 **"base가 끝내지 못하던 문항이 답을 내게 된 것"** 에서 나온다(그림 4). 끝나는 문항의 정확도는 그대로다. 즉 새 지식이 늘었다는 증거는 없다.
3. 맞은 응답만 학습하는 방식(RFT)은 루프를 늘렸고, 나쁜 응답(잘린 응답)을 명시적으로 벌하는 방식(DPO)은 루프를 줄였다.
4. 환경(CUDA 12.9 ↔ 13)이 바뀌어도 점수는 같았다(그림 8).

**한계**: MMMU validation을 여러 후보의 비교에 반복해서 썼으므로 최종 모델을 점수로 고르면 선택 편향(winner's curse)이 있다. 선택에 쓰지 않은 데이터(MMMU test 등)로 확인하지 못했다.

## 2. 학습 방식의 기본 개념

### 2.1 LoRA (Low-Rank Adaptation)
모델 전체(약 45억 파라미터)를 학습하는 대신, 기존 가중치 행렬 W에 **작은 두 행렬의 곱 BA**(랭크 r)를 더해서 W + BA만 학습한다. 우리 설정(r=64)에서는 학습 파라미터가 약 1.3억 개(전체의 2.9%)다.
- **왜 썼나**: 24GB GPU 한 장에서 4B 모델 전체를 학습하기는 메모리가 부족하다. 어댑터만 저장하므로 0.5GB로 보관과 전송이 쉽다.
- 학습 후 어댑터를 base에 더해서(merge) bf16 모델로 저장하고 평가한다.

### 2.2 SFT / RFT (Rejection-sampling Fine-Tuning)
- **SFT**: 정답 응답을 따라 하도록 지도학습한다(교차엔트로피).
- **RFT**: 모델이 직접 만든 응답 중 **정답을 맞힌 것만** 골라서 SFT한다. 자기 증류에 가깝고 "이미 할 수 있는 것을 더 확실하게 만든다".
- 한계(우리 실험에서 확인): 틀린 응답이나 끝나지 않은 응답에 대한 신호가 없다.

### 2.3 GRPO (Group Relative Policy Optimization)
문항 하나에 대해 응답 G개(우리는 8개)를 **현재 모델로 새로 생성**하고, 각 응답의 보상(정답이면 1)을 **그룹 내에서 정규화한 값(advantage)** 으로 모델을 갱신한다(별도의 가치 함수 없음).
- 장점: 정답 여부만으로 학습할 수 있다(규칙 기반 보상).
- 약점(우리 실험에서 확인): (1) 응답을 학습 중에 생성하므로 **최대 길이 상한이 필요**한데, 잘린 응답이 보상 0이면 모델이 "짧게 끝내기"를 배운다. (2) 그룹의 8개가 모두 같은 보상이면(전부 맞거나 전부 틀림) **학습 신호가 0**이다. (3) 생성 때문에 메모리와 시간이 크다.
- 설정: rollout 8, KL 페널티 β(0 또는 0.04), 정답 보상만.

### 2.4 DPO (Direct Preference Optimization)
같은 문항에 대한 **좋은 응답 y_w와 나쁜 응답 y_l의 쌍**으로 학습한다.

L = −log σ( β [ log π(y_w)/π_ref(y_w) − log π(y_l)/π_ref(y_l) ] ) + α · NLL(y_w)

- π는 학습 중인 모델, **π_ref는 기준 모델**(우리는 어댑터를 끈 base). 기준 대비 좋은 응답의 확률은 올리고 나쁜 응답의 확률은 내린다. β=0.1은 기준에서 얼마나 벗어날지의 강도다.
- 둘째 항(α=0.1)은 좋은 응답의 확률이 같이 떨어지는 현상을 막는 보조항(RPO)이다.
- 쌍을 **미리 만들어 두는 오프라인 방식**이라 학습 중에 응답을 생성하지 않는다(GRPO보다 비용이 작음).
- 구현 세부: 응답 위치의 어휘 확률만 계산한다(전체 시퀀스의 로짓 [길이 × 151,936]을 fp32로 만들면 메모리가 폭증).

### 2.5 이 문서에서 자주 쓰는 용어
- **루프(잘림)**: 응답이 32,768토큰 안에 끝나지 않은 것. 같은 말을 반복하거나 "다시 생각해 보면..."을 이어 가는 경우가 많다. 오답으로 채점된다.
- **통과율 k/8**: base로 문항당 8번 풀어서 맞힌 횟수. 0/8과 8/8인 문항은 쌍이나 신호를 만들 수 없다.
- **paired bootstrap**: 같은 문항의 두 모델 점수 차이를 문항 단위로 10,000번 재표집해서 95% 신뢰구간을 구한다.

## 3. 실험별 정리

### E1~E3. GRPO (SSMR-Bench 음악 데이터)

#### 왜 했나
- Music 개선이 목표이므로 음악 데이터로 직접 강화학습했다. **SSMR-Bench 논문(Qwen2.5-VL-7B)이 GRPO로 SSMR 점수 +28.75%p, MMMU Music +6.67%p(Avg@8)를 보고**해서 이를 재현하려 했다.
- 데이터: SSMR-Bench Train_visual(MIT, 규칙으로 만든 합성 음악 문제 4종: Beat, Scale, Interval, Chord). 정답이 자동으로 정해져서 보상 함수를 만들기 쉽다.

#### 어떻게 학습했나
| 항목 | E1 (run1) | E2 (run2) | E3 (run3) |
|---|---|---|---|
| 데이터 | 이미지 1장 문항 중 통과율 1/8~7/8인 **1,120문항** (Beat 365, Scale 315, Interval 280, Chord 160). 문항은 한 번씩만 사용 | 같음 | 같음 |
| 방법 | GRPO, rollout 8, KL 없음(β=0), 정답 보상만 | GRPO, **잘린 응답을 손실에서 제외**, **β=0.04** | E2와 같음 |
| 스텝 | 스텝당 8문항 × **140**스텝 | 8문항 × **60**스텝 | **32**문항 × **15**스텝 (총 480문항 동일) |
| lr, 스케줄 | 2e-5 상수 | 같음 | 같음 |
| 최대 응답 | 2,048토큰 | 2,048 | 2,048 |
| sampling(rollout) | T 0.7, top_p 0.8, top_k 20 (presence_penalty 없음: HF generate가 미지원) | 같음 | 같음 |
| micro-batch / grad accum | 1 / 64 | 같음 | 같음 |
| rollout 생성 | HF generate (24GB에서 vLLM colocate가 맞지 않음) | 같음 | 같음 |
| 시간 | 9.9시간 | 15.4시간 | 16.3시간 |

**왜 이 설정인가**
- 논문은 스텝당 128문항 × 300스텝(38,400문항 분량)인데 우리는 약 1,120문항 분량이다. 24GB와 시간 제약으로 줄였다.
- 이미지 5장 문항은 24GB에서 스텝이 78분 걸리고 메모리 한계라서 1장 문항만 썼다.
- E1에서 점수가 떨어진 뒤 **원인 가설(최대 2,048토큰 + 잘림 보상 0이 "짧게 끝내기"를 보상)을 시험하려고** E2에서 잘림 응답을 손실에서 제외하고 KL을 걸었다. E3는 논문과의 차이 중 "스텝당 규모"만 바꿔 본 것이다.
- E1'(최대 4,096토큰)은 메모리(예약 33GB)가 넘치고 프롬프트 하나에 30분이 걸려서 포기했다.

#### 결과
| | base | E1 | E2 | E3 | E3 5스텝 |
|---|---|---|---|---|---|
| SSMR hold-out (seed 42) | 18.25% | **47.25%** | 32.0% | (정리 안 함) | - |
| MMMU 전체 Avg@2 | 62.83% | **55.39%** | 60.00% | 61.44% | 60.11% (seed 1회) |
| MMMU Music Avg@2 | 23.3% | 25.0%(Avg@4 27.5) | 25.0% | 23.3% | - |
| 잘림 (seed 42 / 43) | 89 / 98 | 66 / 55 | 118 / 128 | 115 / 104 | 112 |

#### 성능이 오르지 않은 원인 분석
데이터로 확인한 것:
1. **SSMR 향상의 98%는 "끝맺음"** 이다(E1). base가 이미 끝내던 171문항은 73 → 75(+2)였고, base가 잘렸던 229문항에서 0 → 114가 됐다. 풀이 실력이 늘었다는 증거는 없다.
2. **응답이 "Step 1, 2, 3 → Answer"의 짧은 정형 틀(약 110~240토큰)로 바뀌었다**(그림 9). base는 쉬운 문항 약 400토큰, 어려운 문항 약 1,050토큰으로 길이를 조절하는데, 학습 모델은 난이도와 무관하게 짧다. MMMU에서 끝낸 문항의 정확도가 약 69% → 약 59%로 내려갔다.
3. **학습 신호가 사라졌다**(그림 9d). 41스텝 이후 문항의 80~89%는 8개 응답이 모두 같은 보상이라 신호가 0이었고, grad_norm=0인 스텝이 33개(모두 41스텝 이후)였다. 보상은 20스텝 만에 0.8에 도달하고 이후 정체됐다.
4. 같은 seed로 base 561 → E1 495(−66문항)이고, **base 잘림이 0~1개뿐인 14과목에서도 −30문항**이어서 하락은 잘림 때문이 아니다.
5. 잘림 제외+KL(E2)로 응답 길이를 유지시키자 하락이 −7.4%p에서 −2.8%p로 줄었다. 그러나 KL과 스텝 수도 함께 바꿨으므로 어느 변경이 기여했는지는 가르지 못했다.
6. E3: base 대비 −1.39%p, 95% 구간 [−3.22, +0.39]로 통계적으로 구분되지 않는다. **5~60스텝, 배치 8~32가 모두 60.1~60.8%로 평탄**하고 base 대비 −1.5~−2%p의 격차가 **5스텝부터** 나타났다. "스텝을 늘리면 오른다"는 근거가 없다.

가설(미검증):
- 학습 중 최대 길이(2,048)와 "잘리면 보상 0"이 "짧게 끝내기"를 보상한다. 잘린 응답이 실제로 길게 추론하는 것이 아니라 끝나지 않는 루프일 가능성이 크다(최악의 프롬프트에서 2,048이든 4,096이든 8개 중 6개가 끝나지 않았다).
- SSMR(규칙으로 만든 합성 문제)에서 MMMU Music(사람이 만든 실제 문제)로 전이되지 않는다.
- 논문과의 차이(스텝당 규모 34배, 8,000문항 전체, 논문의 프롬프트, 전체 파라미터 학습 여부) 중 무엇이 영향을 줬는지는 분리하지 못했다. 논문의 MMMU Music 향상(2문항)은 원래 작아서 우리 신뢰구간(±16%p) 안에 있으므로 "논문과 다르다"고 결론낼 수도 없다.

### E4. RFT (DeepVision 수학, 맞은 응답만)

#### 왜 했나
- E1~E3에서 "음악 데이터 GRPO는 MMMU 전체를 올리지 못했다"는 결론이 나온 뒤, **데이터와 방법을 둘 다 바꿨다.** 방법은 GRPO보다 단순하고 안정적인 지도학습인 RFT, 데이터는 MMMU 전체 점수에 도움이 될 만한 **일반 수학 문제(DeepVision-103K, 2026-02 공개, MIT)** 로 했다.
- DeepVision은 Qwen3-VL(2025-10-11) 이후에 공개돼서 사전학습에 포함됐을 가능성이 낮다(교수님 주의 사항: 공개 이전 데이터는 모델이 이미 봤을 수 있다).
- 같은 시도에서 MMMU와 겹치는 문항은 제거했다(텍스트 유사도, 이미지 pHash).

#### 어떻게 학습했나
| 항목 | 값 |
|---|---|
| 데이터 | DeepVision 77,135 → 변환 가능 54,577 → 풀 12,000 → 중복 제거 11,995. base로 6,000문항을 문항당 8번 풀어(최대 2,048토큰) **통과율 1/8~7/8인 1,897문항**에서 **맞고 끝낸 응답 3,326개**(문항당 최대 2개) |
| 방법 | 응답 위치의 교차엔트로피(지도학습) |
| dv1 | lr 1e-5, grad accum 16, 1에폭 |
| dv2 | lr **3e-6** (3배 낮춤), 나머지 같음 |

**왜 이 설정인가**: 통과율 0/8과 8/8 문항은 제외했다(각각 모두 틀림/모두 맞음이라 정보가 약함). dv2는 dv1이 나빠진 이유가 "학습률이 너무 커서"인지 확인하려고 만들었다.

#### 결과
| | base | RFT dv1 | RFT dv2 |
|---|---|---|---|
| MMMU 전체 (seed 42) | 62.33% | **56.89%** | (전체 평가 안 함) |
| 루프(잘림+오류) | 89 | **209** (잘림 164 + 오류 45) | - |
| 4과목 진단 루프(120문항) | 31 | 72 | **61** |
| Music | 7/30 | 1/30 | - |

- dv1은 seed 1회이고 오류 45건이 오답으로 계산된 값이다. dv2는 Electronics, Materials, Mechanical, Music 4과목 120문항만 평가했다(그림 10).

#### 성능이 오르지 않은 원인 분석
데이터로 확인한 것:
- **루프가 늘었다**(89 → 209). 점수 하락이 루프 증가와 같이 움직였다(그림 3).
- **학습률 때문이 아니다**: 학습률을 3배 낮춰도 루프는 72 → 61로 거의 그대로였다.
- 길이 편향("긴 응답이 더 많이 선택됐다")과 재고 표현("Wait", "Actually" 같은 hedge 표현의 증폭) 가설은 데이터로 기각했다. 학습 손실이 0.2 → 0.11로 내린 것은 데이터 수준의 값이지 모델이 날카로워졌다는 증거가 아니었다.

가설(미검증): **맞은 응답만 학습하면 "끝나지 않는 풀이를 벌하는 신호"가 없다.** 모델은 이미 가진 능력을 강화하는데, 맞고 끝난 응답은 루프에 빠지는 경향과 무관하게 선택되어 루프 경향이 그대로 남거나 강화된다. 이 가설이 DPO로 넘어간 직접적인 이유다.

### E5. DPO (DeepVision 수학 쌍)

#### 왜 했나
- RFT의 실패 원인 가설을 직접 시험하기 위해 **나쁜 응답, 특히 끝나지 않은 루프 응답을 명시적으로 나쁜 쪽에 두는** 선호 학습을 썼다. 같은 base 응답 샘플(통과율 측정 때 저장한 8개)을 재사용해서 새로 생성하는 비용이 없다.
- GRPO가 아니라 DPO를 택한 이유: GRPO는 학습 중 생성이 필요해서 길이 상한과 잘림 보상 설계가 결과를 좌우하고(E1~E3), 24GB에서 비용이 크다. DPO는 **쌍을 미리 만들어서 길이 상한의 영향을 직접 통제**할 수 있다.

#### 어떻게 학습했나
**쌍 구성**(`build_dpo.py`)
- 좋은 응답(chosen): 맞고 끝난(finish_reason=stop) 응답 중 무작위(반복 줄이 있는 응답 제외, 12,000자 이하)
- 나쁜 응답(rejected): **60% 확률로 잘린 응답을 우선**, 없으면 틀린 응답
- 문항당 쌍 1개, 통과율 1/8~7/8만 → **1,897쌍** (잘린 응답 1,271 / 틀린 응답 626)

| 항목 | 값 |
|---|---|
| 방법 | DPO + 좋은 응답의 NLL 보조항 |
| β / NLL 가중치 | 0.1 / 0.1 |
| 기준 모델 | 어댑터를 끈 base (별도 사본 불필요) |
| lr | 5e-6, cosine, warmup 3스텝 |
| 배치 | micro-batch 1쌍, grad accum 16쌍 → **119스텝** |
| 에폭 / seed | 1 / 42 |
| 시간 | 4,998초(원본), 4,684초(재학습) |
| 메모리 대책 | 응답 위치의 어휘 확률만 계산, 기준 계산 뒤와 매 스텝 뒤 `empty_cache` |

**왜 이 설정인가**: 낮은 lr(5e-6)과 1에폭은 RFT보다 보수적으로, 모델이 base에서 크게 벗어나지 않게 하려는 것이다. NLL 보조항은 RFT 때 "좋은 응답만 학습"이 문제였으므로 작게(0.1) 두었다.

#### 결과
| | base (cu129) | DPO dv1 원본 | DPO dv1_re (재학습) |
|---|---|---|---|
| MMMU 전체 Avg@2 | 62.83% | **65.94%** (+3.11%p [+1.33, +4.94]) | 65.11% (+2.28%p [+0.56, +4.00]) |
| 잘림 (seed 42 / 43) | 89 / 98 | 33 / 26 | 29 / 35 |
| Music Avg@2 | 23.3% | 40.0% | 31.7% |

- 원본 어댑터는 로컬로 옮기는 중 마지막 150MiB가 0으로 채워져 손상됐고(해시와 0 블록 검사로 발견), **같은 쌍과 같은 설정으로 재학습**한 것이 `dv1_re`다. 원본과 재학습은 통계적으로 구분되지 않는다(−0.83%p [−2.56, +0.89]). 즉 같은 설정의 반복에서도 base를 넘었다.

#### 성능이 오른 원인 분석
데이터로 확인한 것:
- **이득은 루프 해소에서 나온다**(그림 4, 표 4). `dv1_re`(cu130) 기준 base가 끝내지 못한 문항 80개에서 정답이 2 → 37로 늘었고(+35문항), 둘 다 끝낸 787문항에서는 547 → 549(+2.0)로 사실상 그대로였다. 새로 끝내지 못하게 된 문항은 8개(정답 5 → 0).
- 같은 효과가 **음악 hold-out에도 전이**됐다(그림 7). DeepVision 수학으로만 학습했는데 악보 문항의 잘림이 124 → 38로 줄고 전체가 52.7% → 62.4%로 올랐다. 즉 루프 억제는 데이터 종류를 가리지 않는다.
- 4과목 진단에서 루프가 base 31, RFT 72(dv1), 61(dv2), **DPO 14**였다(그림 10).

가설: 잘린 루프 응답을 직접 나쁜 쪽에 놓은 것이 "끝나지 않는 풀이"의 확률을 낮췄고, 이 습관이 문제 유형과 무관하게 전이됐다. 다만 **끝낸 문항의 정확도가 오르지 않은 것으로 보아 새 지식이 들어간 증거는 없다**(제안한 "지식 보강" 해석은 이 데이터로 뒷받침되지 않는다).

#### 환경 강건성
- `dv1_re`를 cu129(transformers 5.19.0)와 cu130(transformers 5.22.2)에서 같은 seed로 평가하면 정답 수가 586/586(seed 42), 586/587(seed 43)이었다.
- 문항별로는 같은 정오가 87.6~88.1%였고, 이는 **같은 환경에서 seed만 바꿨을 때의 일치도**(DPO 84.8%, base 86.1%)와 같은 수준이다(그림 8, 표 8). 환경을 바꾸는 것은 seed를 바꾸는 것과 비슷한 정도의 교란이다.

### E6. DPO (DeepVision + MusiXQA 쌍, 제출 모델)

#### 왜 했나
- 목표에 **Music 개선**이 있으므로, DPO가 통하는 것이 확인된 뒤 음악 데이터를 같은 방식으로 섞었다. 앞서 GRPO(SSMR)가 실패했던 영역을 검증된 방법(DPO)으로 다시 시도한 것이다.
- 데이터로 **MusiXQA**(puar-playground, MIT, 합성 악보)를 택한 이유: 악보 이미지에서 음 높이, 조표, 마디 수, 음자리표를 묻는 문항으로 변환하면 정답이 자동으로 정해지고, 팀원이 이미 객관식(학습 3,200 + hold-out 400)으로 만들어 두었다. MMMU Music과 중복도 없다(dev/validation/test 대조에서 제거 0건).
- 한계: MusiXQA는 2025-07-07 공개로 Qwen3-VL(2025-10-11)보다 이전이라 모델이 이미 봤을 수 있다(교수님 주의 사항, 규칙은 아님). 또 악보 "읽기"는 MMMU Music과 유형이 다를 수 있다.

#### 어떻게 학습했나
**MusiXQA 쌍**
- 학습 3,200문항(PitchReading 1,920, KeySignature 800, MeasureCount 320, Clef 160) 중 PitchReading, KeySignature, MeasureCount만 base로 문항당 8번 풀어(최대 2,048토큰) 통과율 1/8~7/8에서 쌍을 만들었다. Clef는 base가 이미 98%라 신호가 거의 없어 제외했다.
- 선별 소요: PitchReading 약 6.8문항/분(응답이 2,048토큰까지 가서 가장 느림), KeySignature 약 26문항/분, MeasureCount 약 10문항/분. 전체 약 3시간 15분.
- 통과율 분포(1~7/8 비율): PitchReading 43%(1,098문항 중 474), KeySignature 59%(800문항 중 470), MeasureCount 36%(320문항 중 116). PitchReading은 일정상 1,920문항 중 1,098문항(57%)만 풀었고, 파일럿 100문항에서는 58%가 8번 모두 틀려서 쌍을 만들 수 없었다.
- **MusiXQA 쌍 1,052개**(PitchReading 466, KeySignature 470, MeasureCount 116; 잘린 응답 761 / 틀린 응답 291).

| 항목 | 값 |
|---|---|
| 학습 데이터 | DeepVision 쌍 1,897 + MusiXQA 쌍 1,052 = **2,949쌍**(잘린 2,032 / 틀린 917, 섞어서 seed 42로 셔플). 섞은 파일 SHA-256 `a1b386dd6ff753383b26b5c83a1edba03b9b3e54594da26ae298e2d2c233b147` (`music_ft/mix_dpo.py`가 입력 두 파일에서 바이트 단위로 같은 파일을 만든다) |
| 설정 | E5와 같음(lr 5e-6, β 0.1, NLL 0.1, grad accum 16) |
| 스텝 / 시간 | **185스텝 / 8,321초**(스텝당 약 45초, E5는 39초) |
| 체크포인트 | 20스텝마다, 최근 3개 |
| 어댑터 SHA-256 | `4492c406fe29110a3c7b219890ee80d50bf1981b82956cedea27a00887acd131` |

**왜 이 설정인가**: E5와 같은 설정을 유지해서 **데이터만 바꾼 비교**가 되게 했다. MusiXQA 쌍과 DeepVision 쌍을 섞은 것은 음악 쌍만 쓰면 수학 쌍의 효과(일반 루프 억제)를 잃을 수 있어서다.

#### 결과 (cu130, 같은 환경)
| | base | DPO(DV) | **DPO(DV+MusiXQA)** |
|---|---|---|---|
| MMMU 전체 Avg@2 | 61.56% | 65.17% | **65.89%** |
| Music Avg@2 | 18.3% | 31.7% | **43.3%** (13/30, 13/30) |
| 잘림 | 105 / 104 | 30 / 35 | **10 / 17** |
| 요청 오류 | 0 / 0 | 0 / 0 | 0 / 0 |
| 악보 hold-out 전체 (cu129, 2 seed 평균) | 52.7% | 62.4% | **66.5%** |
| 악보 hold-out 잘림 | 124 | 38 | **12** |
| 악보 hold-out PitchReading | 17% | 39.5% | **54%** |
| 악보 hold-out 끝까지 답한 문항의 정확도 | 76.4% | 68.9% | 68.5% |

- base 대비 전체 +4.33%p [+2.44, +6.22], Music +25.0%p [+10.0, +40.0]로 **둘 다 신뢰구간이 0 위**다. `DPO(DV)` 대비로는 전체 +0.72%p [−1.00, +2.44]로 구분되지 않고 Music +11.7%p [0.0, +23.3]는 하한이 0이다.

#### 성능이 오른 원인 분석
- 데이터로 확인: MMMU 이득(+39.0문항, 2 seed 평균)의 **거의 전부가 루프 해소**(base가 끝내지 못한 94문항에서 정답 2 → 42, +40.5)다. 둘 다 끝낸 792문항은 549 → 550(+1.0)다. 루프가 `DPO(DV)`보다 더 줄었다(잘림 30~35 → 10~17).
- 악보 hold-out에서 **잘림이 124 → 12**로 줄고 PitchReading이 17% → 54%로 가장 크게 올랐다. 학습 쌍의 44%(466개)가 PitchReading이었고 base가 가장 못하던 유형이라 방향이 맞다.
- **"끝까지 답한 문항의 정확도"는 오르지 않았다**(76.4% → 68.5%). 지식 보강이었다면 이 값이 올라야 한다. 다만 이 모델은 이전에 못 끝내던 어려운 문항을 끝내므로 **끝난 문항의 구성이 더 어려워서** 값이 눌렸을 수 있다. 같은 문항 안에서의 비교(base와 둘 다 끝낸 문항만)는 아직 하지 않았다.
- 결론(조심스럽게): MusiXQA 쌍은 루프를 더 줄이고 악보 문항 점수를 올렸지만, **악보 읽기 능력(지식)이 늘었다는 증거는 없다.** MMMU Music의 개선(+25.0%p)이 루프 억제 때문인지 악보 지식 때문인지는 구분하지 못했다.

### E7. MusiXQA GRPO (팀원)

#### 왜 했나 / 어떻게 학습했나
팀원이 MusiXQA 객관식으로 직접 GRPO를 수행했다. 학습 설정 중 **기록에서 확인된 것**과 **확인하지 못한 것**을 구분한다.
| 항목 | 값 |

| lr | 2e-5 상수 (`trainer_state.json`의 학습률 값) |
| LoRA | r=64, α=128, 같은 대상 모듈 (`adapter_config.json`) |
| 체크포인트 | 10스텝마다 |
| 데이터 구성, rollout 수, 최대 응답 길이, 보상 세부 | **미확인**(코드는 우리 `train_grpo.py`와 같아서 팀원이 설정을 바꿨을 수 있으나 기록이 없음) |
| 어댑터 SHA-256 | `86b4408467c53a6d0667bb95ff0c564b858d1a677139b921fbba6c16364580f8` |

#### 결과
| | 팀원 보고(팀원 환경 cu130, WSL, seed 42) | **우리 환경 cu130**(Avg@2) |
|---|---|---|
| 전체 | 64.22%, 64.56%(같은 seed 재평가) | **64.33%** (63.67 / 65.00) |
| 잘림 | 4, 2 | **2 / 2** |
| Music | 12/30, 11/30 | **10/30, 10/30** (33.3%) |

- 우리 환경에서 팀원의 보고값이 재현됐다. 팀원의 base는 59.67%(잘림 107)로 우리 cu129/cu130 base(62.8%/61.6%)보다 낮아서, 팀원이 보고한 "+4.55%p"는 우리 환경에서는 **+2.78%p**[+0.67, +4.89]로 줄었다.

#### 성능이 오른 원인 분석
- **학습 로그**(그림 9): 응답 길이가 1,435 → 약 250토큰으로 급감하고 잘린 응답 비율이 62.5% → 0이 됐으며, 후반에는 모든 그룹의 보상이 같아져(`frac_reward_zero_std` 100%, `grad_norm` 0) 학습 신호가 사라졌다. **우리 GRPO run1과 같은 현상**이다.
- 그런데 우리 run1은 끝낸 문항의 정확도가 69% → 59%로 떨어져 점수가 하락한 반면, 팀원 모델은 **끝낸 문항의 정확도가 거의 그대로**(둘 다 끝낸 794문항에서 552 → 539, −12.5문항, 약 −1.6%p)이고 base가 끝내지 못한 104문항에서 2 → 40으로 올랐다(그림 4).
- 가설: 학습 데이터가 같은 짧은 정형 틀을 강화하더라도 **데이터와 보상 설계(MusiXQA는 모든 문항이 객관식 4지선다 악보 읽기)** 가 달라서 MMMU 문항 전반에 미치는 부작용이 달랐을 수 있다. 어느 요인이 차이를 만들었는지는 이번 자료로 분리할 수 없다.
- 40스텝만 학습했고 후반 신호가 사라졌으므로 학습량을 늘려도 달라지지 않았을 것으로 보이나 확인하지 않았다.

#### 악보 hold-out 결과 (표 6, 그림 7, cu129, 2 seed 평균)
| | base | **MusiXQA GRPO(팀원)** | DPO(DV) | DPO(DV+MusiXQA) |
|---|---|---|---|---|
| 전체 | 52.7% | **72.3%** (72.8 / 71.8) | 62.3% | 66.5% |
| 잘림 | 124 | **0** | 38 | 12 |
| 끝까지 답한 문항의 정확도 | 76.4% | 72.2% | 68.9% | 68.5% |
| PitchReading | 17% | **78%** (79 / 76) | 40% | 54% |
| KeySignature / MeasureCount / Clef | 48 / 48 / 98 | 55 / 60 / 96 | 56 / 57 / 96 | 60 / 56 / 96 |

- **악보 읽기 홀드아웃에서는 팀원 GRPO가 가장 높다**(72.3%, PitchReading 78%). MusiXQA 학습 데이터와 **같은 분포**이므로 오르는 것이 당연한 비교이고, 우리 DPO(DV+MusiXQA)보다 약 6%p 높다.
- 그러나 **MMMU 전체와 Music에서는 팀원 모델이 우리 DPO와 구분되지 않거나 낮다**(전체 64.33% 대 65.89%, Music 33.3% 대 43.3%). 즉 **악보 읽기 홀드아웃 점수가 MMMU Music 점수로 이어지지 않았다.** 합성 악보 읽기와 MMMU Music(사람이 만든 실제 문제) 사이의 분포 차이가 병목일 수 있다는 앞의 가설과 맞는 결과이지만, 이 자료로 검증하지는 못했다.
- 끝까지 답한 문항의 정확도는 세 모델 모두 base(76.4%)보다 **낮다**(72.2%, 68.9%, 68.5%). 이 값만으로 지식 보강이 없었다고도 있었다고도 단정할 수 없다(끝난 문항의 구성이 다르기 때문이며, 같은 문항 안에서의 비교는 하지 않았다).
- 팀원 모델은 잘림이 0이다. 응답을 짧은 틀로 끝내도록 학습된 영향으로 보인다.

## 4. 종합 분석

### 4.1 성능이 오르지 않은 실험의 공통 원인
| 실험 | 루프 | 끝낸 문항 정확도 | 결과 |
|---|---|---|---|
| GRPO run1 | 감소 (89→66, 98→55) | **하락** (약 69% → 약 59%) | −7.4%p. 짧은 정형 틀로 풀이가 바뀜 |
| GRPO run2/run3 | **증가** (run2 118/128, run3 115/104, base 89/98) | 하락 | −1.4~−2.8%p, 5스텝부터 격차 |
| RFT dv1/dv2 | **증가**(89→209) | - | −5.9%p. 맞은 응답만 학습해서 루프 억제 신호 없음 |

### 4.2 성능이 오른 실험의 공통 원인
| 실험 | 루프 해소로 얻은 문항 | 끝낸 문항의 변화 | 합계 |
|---|---|---|---|
| 팀원 GRPO | +38 | −12.5 | +25.0 |
| DPO(DV) | +35 | +2.0 | +32.5 |
| DPO(DV+MusiXQA) | +40.5 | +1.0 | +39.0 |
(표 4, cu130, 같은 seed끼리 짝지은 2 seed 평균, 단위: 정답 수. base 최종본 기준)
- 세 모델 모두 이득은 루프 해소에서 나온다. **끝낸 문항의 정확도를 유지하면서** 루프를 해소하는 방법이 성공했고, 루프는 줄었으나 끝낸 문항의 정확도가 떨어지는 방법(GRPO run1)은 실패했다.

### 4.3 한계와 열린 질문
1. **지식 보강 여부**: 끝낸 문항의 정확도가 오르지 않았다. "음악 지식이 늘었는가"는 확인하지 못했다. 같은 문항 안에서 base와 비교하는 분석(둘 다 끝낸 문항만)과 별도의 음악 지식 측정이 필요하다.
2. **선택 편향**: 여러 후보를 MMMU validation으로 비교했고 가장 높은 것을 제출한다. 세 모델 사이의 점수 차이는 구분되지 않는다. 선택에 쓰지 않은 데이터로는 확인하지 못했다.
3. **Music 30문항**: base의 Music도 두 seed에서 3/30, 8/30(재시도 후)으로 흔들린다. 같은 환경의 base 대비 Music 차이는 팀원 GRPO +15.0%p [+5.0, +26.7]와 **제출 모델 +25.0%p [+10.0, +40.0]만 신뢰구간이 0 위**이고, DPO(DeepVision)는 +13.3%p [−1.7, +30.0]로 0을 포함한다. 즉 Music 개선은 방향은 세 모델 모두 같지만, 크기가 확실한 것은 MusiXQA를 학습한 두 모델뿐이다.
4. **환경**: 학습과 응답 선별은 CUDA 12.9(cu129, transformers 5.19.0)에서, 최종 MMMU 평가는 CUDA 13(cu130, transformers 5.22.2)에서 했다. 같은 모델을 두 환경에서 평가했을 때 점수는 같았다(그림 8). 악보 hold-out은 cu129 값이다(표 7). 학습 환경 기록 중 `dpo_dvmx1`은 평가가 덮어써서 `mmdl` 환경에서 다시 만든 파일(`train_env_pip_freeze_mmdl.txt`)로 보완했다.
5. **팀원 모델**: 학습 설정(rollout 수, 데이터 구성, 보상 세부)을 확인하지 못했다. 팀원 GRPO의 악보 hold-out은 첫 시도에서 다른 작업이 GPU 메모리를 점유해(여유 2.45GiB) vLLM 서버가 뜨지 못했고, 같은 명령을 다시 실행해 측정했다(환경 문제가 아니라 실행 순서 문제).
6. **데이터 공개일**: SSMR-Bench(2025-09-06)와 MusiXQA(2025-07-07)는 Qwen3-VL(2025-10-11)보다 앞서서 모델이 이미 봤을 수 있다. DeepVision(2026-02)은 이후다.
7. **데이터 규칙 준수**: MMMU validation과 test는 학습에 쓰지 않았고, 모든 외부 데이터는 MMMU와 텍스트 유사도와 이미지 pHash로 중복을 제거했다.
