# MusiXQA 샘플 검수 반영 — 2026-11-08

후속 지시: 사용자가 팀 확인을 건너뛰도록 명시했다. 아래 80문항 검수 기록은 유지하고,
현재 데이터 구성은 [pilot20 기반 조정안](musixqa_pilot20_recipe.md)을 따른다.

대상: `data/musixqa_mcq_sample/`, 학습 64 + holdout 16문항.
검수 근거: 사용자가 악보 80장을 직접 대조해 작성한 `manual_review.csv`와 대화 보고.
사용자의 최초 판정은 통과 78 / 수정 필요 2였다. 두 질문을 수정한 뒤 사용자 재확인이 완료되어 현재 판정은 **80/80 통과**다.
에이전트는 해당 두 악보의 첫 인쇄 마디 번호가 2인 것을 별도로 확인했다.

## 1. 수정한 질문

| 문항 ID | 문서 | 수정 |
|---|---|---|
| `musixqa_train_00038` | `0019023` | `bar 1` → `the first visible bar (printed bar number 2)` |
| `musixqa_holdout_00009` | `0087904` | `bar 1` → `the first visible bar (printed bar number 2)` |

두 문항의 질문만 바뀌었다. 기존 정답, 선택지 순서, ID, 이미지, 나머지 78문항이 동일한지 비교했다.
원본 QA의 `source_question`과 난수 선별용 identity는 그대로 두고 실제 출력 질문을 별도로 기록했다.
빈 1마디 때문에 생긴 문제인지는 확인하지 못했다. 관찰 사실은 원본 QA가 1st bar를 지칭하는데
첫 번째로 보이는 마디의 인쇄 번호가 2이고, 사용자가 원본 정답 음열이 그 마디와 일치함을 확인했다는 것이다.

변경 이력: 샘플 폴더의 `question_revisions.json`.
원본 기록 백업: `data/musixqa_mcq_sample_before_bar_reference_fix/` (이미지는 수정하지 않아 별도 복사하지 않음).
CSV에는 이전 fix 사유를 메모로 남기고, 두 문항의 재확인 결과를 pass 및 `question_updated_rechecked_pass`로 기록했다.
manifest에도 검수 완료 80건, pass 80건, 재확인 대기 0건을 반영했다. 팀 확인 단계는 후속 사용자 지시로 면제한다.

## 2. 마디 번호 재발 방지 범위

- 생성기에 검수로 확인된 세 문서 `0019023`, `0087904`, `0060047`을 등록했다.
- 첫 두 문서의 원본 1st bar 질문만 위치를 명확히 표현한다.
- 해당 문서들의 다른 마디와 `0060047`의 PitchReading은 대응 관계가 검증되지 않아 후보에서 제외한다.
- MeasureCount 등 다른 카테고리를 문서 단위로 일괄 제외하지 않는다.
- `quality_report.json`에 원본 1st bar 및 등록된 문서의 위치 확인 목록을 기록한다.

이것은 알려진 문서 검사와 검수 대상 표시이며, 전체 PNG에서 마디 번호를 자동 판독하는 OCR 검사는 아니다.
전수 자동 검출에는 실제 첫 인쇄 번호를 읽는 검출기를 만들고 누락·오탐을 검증해야 한다.
등록된 세 문서만 제외하면 미발견 문서까지 해결된 것으로 간주하면 안 된다.

## 3. 검수 해석 규칙

- MeasureCount: 반복 연주를 제외한, 악보에 실제 적힌 마디 수. 사용자 보고상 반복 기호가 있는 12문항도 이 기준으로 검수했다.
- `musixqa_train_00027` / 문서 `0060047`: 첫 번호 2, 마지막 번호 15지만 실제 14마디라는 사용자 검수를 보존했다.
  마지막 인쇄 번호를 마디 수로 바로 쓰는 검증은 금지한다.
- PitchReading: 붙임줄 양쪽의 적힌 음표를 각각 센다. 소리의 재발음 횟수와 구별한다.
- 검수 화면의 안내에도 위 해석을 반영했다.

## 4. 내용 분포와 Clef 한계

| 항목 | 샘플 20문항 |
|---|---|
| Clef | both 13, treble only 4, bass only 3 |
| KeySignature | 7 flats 5 (25%); 전체 세부 분포는 quality_report.json |
| A/B/C/D 위치 | 각 카테고리 각각 5개씩 (25%) |

정답 글자 균형과 정답 내용 균형은 서로 다른 조건이다.
생성기에 `--balance-content` 옵션을 추가했다. 새 데이터 생성 시 각 분할의 Clef와 KeySignature에서
후보 풀에 존재하는 정답 내용별 개수를 최대한 균등하게 선별한다. 샘플 선별 결과가 바뀌므로 이번에 검수한 80문항에는 소급 적용하지 않았다.
원본에 존재하지 않는 정답 유형을 새로 만들지는 않는다.

원본 train/test의 simple QA 전체에서 Clef 라벨을 집계한 결과:

| 원본 라벨 | train | test |
|---|---:|---:|
| both treble and bass | 43,303 | 4,760 |
| treble only | 32,354 | 3,678 |
| bass only | 10,743 | 1,162 |
| alto only | 0 | 0 |

근거 파일: 샘플 폴더의 `source_clef_distribution.json`. 이는 원본 QA 라벨 집계이며 96,000장 이미지의 직접 검수를 의미하지 않는다.
`alto clef only`는 요청서에 지정된 선택지이지만 정답 라벨로 등장하지 않는다. 따라서 학습 시 제외 가능한 선택지가 되어
실질적으로 세 정답 유형만 남는다는 한계가 있다. 균등 선별로 이 문제까지 해결되는 것은 아니다.
이 카테고리의 유지·비중·추가 데이터 확보는 팀과 결정할 사항이다.
